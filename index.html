常见问题

这些问题大多是试用时第一分钟就会冒出来的
为什么只有 118 首歌？
因为曲库规模不是技术问题，是数据和版权问题。这 118 首全部是公有领域作品， 可以合法完整展示；而要收录一首流行歌，得先解决词曲授权。 技术上再加 200 首也跑得动，但检索要换成倒排索引才不卡——那是下一阶段的事。
为什么 education、technology 这类词查不到？
因为民谣不唱这些词。实测 38 个四六级抽象词，38 个命中 0 句。 这不是算法缺陷，是题材决定的边界：歌里唱的是 love / river / night / home。 所以本工具定位在基础具体词，不承诺学术词覆盖——把边界说清楚，比宣称"什么都能查"可信。
听到的是真人唱的吗？
不是录音，是人声合成。整个应用不含任何音频文件——录音制品有版权，旋律没有， 所以旋律和"唱"都是打开页面那一刻算出来的：

① 旋律：86 首配了传世曲谱，用振荡器现场演奏（八音盒音色 + 低音垫）； 另外 32 首多为念谣类童谣、本无固定曲调，按歌词音节现场哼一段五声音阶，界面会标明"即兴哼唱"。

② 唱：每个音符唱一个音节。发声体是"声门源 + 三段共振峰"——锯齿波当声带， 三个带通滤波器当口腔，中心频率取 a / e / i / o / u 的第一、二、三共振峰； 元音从单词拼写里取（home → o，happy → a 再 i），一个词有几个音节就换几次口型。 词首补一点辅音噪声（s 是沙沙、p 是短爆），词内音符之间做 55ms 滑音，颤音延迟 0.18 秒才起振。 人声比八音盒低八度——这些民谣多在 G4–E5，照原调唱谐波太稀，元音反而听不清。 具体低几个八度按整句音区算，让"最高的那几个音"也落在 350Hz 以下。

③ 那条金线：每句歌词下面画着它的音高走势——阶梯越高，唱得越高； 每个音起点有一个小点。它和声音用的是同一份时间轴，所以点播放时， 亮线从左推到右、词一个个亮起来、曲线正好走到那个词，三件事是同步的。

所以它确实在"唱这个词"，但不是真人：没有发音词典，辅音只是点缀，咬字不如 TTS 清楚。 想只听旋律、想听最清楚的发音，播放条上有「人声 / 乐声 / 朗读」三档开关（朗读=系统语音引擎正常读这句，逐词点亮），句子右侧的 🔊 则任何时候都直接朗读。
展示歌词不会侵权吗？
曲库全部为公有领域作品（传统民谣、灵歌、童谣与 18–19 世纪创作歌曲），著作权保护期已届满， 可合法完整展示。另外结果页每首歌只呈现命中目标词的那一句，不做整首歌词的批量输出。
和 LyricsTraining 有什么不同？
它是歌曲驱动：先选一首歌，再学这首歌里的词。 本项目是需求驱动：你手上有自己的单词表，反过来找"这个词在哪首歌里被唱过"。 方向相反，解决的是不同的场景——所以才有'粘贴单词表算覆盖率'这个功能。
搜 save 能搜到 saved 吗？
能。做法不是简单去掉词尾，而是先生成候选、再回曲库词表验证： eyes → ey / eye 取真实存在的 eye， running → runn / run 取 run， roses → rose 而不会被误判成 rise。 复合词也做了拆分：riverside → river + side。
我的数据会被上传吗？
不会。整个应用是纯前端，没有后端、没有数据库， 粘贴的单词表只存在于当前页面的内存里，关掉即消失。 查询词会写进地址栏（方便把链接发给别人），但不会发往任何服务器。
关于版权
曲库全部为公有领域作品（传统民谣、灵歌、童谣与 18–19 世纪创作歌曲）， 著作权保护期已届满。
关于声音
不加载任何录音文件 —— 旋律由 Web Audio 现场合成， 歌词由浏览器语音引擎朗读。声音里没有第三方录音，因此没有录音制品权问题。
匹配规则
大小写不敏感；词形还原采用「候选 + 曲库词表验证」， eyes → eye、running → run、dried → dry、riverside → river + side。
结果呈现
每词精选 5 句，来源分散在不同歌曲，避免一屏几十句刷屏。
